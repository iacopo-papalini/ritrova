A source first ingested with wrong or missing dimensions or EXIF keeps them forever, `--force` included. **Verified.**

- ⚠️ `src/ritrova/describer.py:406` — `describe_sources` calls `record_scan(source_id, "describe", ...)` but only deletes prior describe scans when `force` is set. - ❓ `src/ritrova/analysis_steps.py:151` — `DeduplicationStep` is documented as a post-processing pass but the CLI composes it as an ordinary per-frame step, so it re-runs an O(n²) comparison over all accumulated findings on every sampled video frame. - ❓ `src/ritrova/analysis.py:311` — video frame filenames use a 10-hex-digit truncated MD5 of the relative path. Two colliding videos would overwrite each other's cached frames with no detection.
- ❓ `src/ritrova/cli.py:430` — EXIF `taken_at` and GPS are read for photos only, so video sources always have `taken_at = NULL` and depend entirely on path parsing. Nothing states whether that is intended.
- 🔍 gap — `src/ritrova/cli.py:448` — the per-source `except OSError` does not cover model-runtime failures (ONNX/CoreML/MLX errors, non-`OSError` `cv2` decode errors), so one bad source aborts the whole run at `future.result()` and loses the remaining queue.

- ⚠️ `src/ritrova/db/maintenance.py:132` — `export_json` selects unnamed findings with `WHERE fa.subject_id IS NULL`, which also matches `stranger` and `not_a_face` rows, so dismissed detections are exported as unnamed faces.

### Clustering and assignment

- ⚠️ `src/ritrova/cluster.py:314` — `auto_assign` builds `centroid_matrix` filtered to the kind's dimension, but `_findings_centroid(findings)` picks the cluster's majority dimension with no dim argument. A cluster whose species label was corrected while its embeddings stayed in the other vector space yields a mismatched shape, so `centroid_matrix @ cluster_centroid` raises instead of skipping the cluster. `rank_subjects_for_cluster` documents exactly this label/space divergence.
- ⚠️ `src/ritrova/cluster.py:110` — `-1` is overloaded as both "unvisited" and "noise" in `_cluster_faiss`. Faces rejected by the complete-linkage verification of their own component are later treated as unvisited BFS starts, so the leftovers of an already-processed component are re-explored and can form a cluster among themselves.
- ⚠️ `src/ritrova/cluster.py:421` — `auto_merge_clusters` iterates a suggestion list computed once. After merging B into A, a later pair (B, C) still names B, so C's findings move into a now-empty cluster id; transitively similar groups do not end up together in one pass and `faces_moved` double-counts from stale sizes. The CLI hides this by looping to convergence; a direct call or the `auto-merge` command does one pass only.
- ⚠️ `src/ritrova/cluster.py:417` — `auto_merge_clusters` calls `suggest_merges`, which builds centroids for every named subject and then discards every pair involving a subject. At 61K+ faces each pass loads up to 500 embeddings per subject for nothing, and the CLI runs up to 20 passes.
- ⚠️ `src/ritrova/services_domain/curation_service.py:175` — `restore_from_stranger` called without `finding_ids` selects every finding in the DB with `exclusion_reason = 'stranger'` and puts them all into the single `cluster_id` argument. The docstring says this is only safe immediately after `mark_cluster_stranger`; nothing enforces it. It also issues raw SQL through `self._db.conn`, bypassing the `FaceDB` method layer the module's own rules reserve for SQL.
- ⚠️ `src/ritrova/services_domain/curation_service.py:153` — `exclude_findings_from_cluster` is the only mutating method in the service not wrapped in `db.transaction()`, against the one-transaction-per-mutation rule in the package docstring. **Verified.**
- ❓ `src/ritrova/cluster.py:184` — `cluster_faces` defaults `threshold=0.45` while `cli.py:938` passes 0.50 for humans and 0.23 for pets. Two sources of truth; any non-CLI caller silently gets the looser value. **Verified.**
- ❓ `src/ritrova/cluster.py:41` — `_findings_centroid` returns a zero vector of hardcoded 512 dims for empty input. Callers then infer kind from `len(centroid)`, so an empty pet subject is treated as a person and scores 0.0 against everything rather than erroring.
- ❓ `src/ritrova/app/routers/clusters.py:197` — `name_cluster` registers the delete-subject undo via `create_subject_and_register_delete` before calling `db.assign_cluster_to_subject`, and the two are not in one transaction. A failure between them leaves a named subject with no findings and an undo token whose description claims N faces were assigned.
- ❓ `src/ritrova/hints.py:17` — `hints.py` imports the private `_findings_centroid` from `cluster.py`, and `cluster.py:536` / `hints.py:61` reach into `db._kind_for_species` with `noqa: SLF001`. Three private-boundary crossings in the read-side scoring path.
